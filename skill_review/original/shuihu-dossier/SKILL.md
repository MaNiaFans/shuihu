# 水浒人物深度档案

## 这个 skill 解决什么问题

《水浒传》用白描写故事,不点评、不交代心理。读者的视线被主角带着走,于是大量配角的动机、旁观者的反应、「恰好不在场」的人、反复出现的小物件都被忽略。本 skill 先把全书按**场景→人物**拆成可检索的结构化记录,再按人物聚合,最后在严格的证据纪律下做解读。

三条原则贯穿全程:

1. **证据先行**:每条事实性陈述必须带「回目-场景号 + 原文片段」,片段由脚本核对,不靠模型自评。
2. **分层标注**:事实、推断、评点、猜想四层不得混写。
3. **写的人和审的人分开**:抽取有审稿,撰写有终审,审稿员独立上下文、先盲读后对照。

## 角色与文件

| 角色 | 职责 | 读哪个文件 |
|---|---|---|
| 抽取员 | 一回一回地读,切场景,逐场景结构化记录 | `references/role_extractor.md` |
| 场景审稿员 | 盲读对照抽取结果,找漏人、错归属、编造 | `references/role_scene_reviewer.md` |
| 档案撰写员 | 依聚合结果写人物档案 | `references/role_dossier_writer.md` |
| 终审审稿员 | 查引文支持度、分层纪律、完整性、污染 | `references/role_final_reviewer.md` |

辅助资料:

- `references/schema.md`:所有数据格式,**动手前必读**
- `references/reading_techniques.md`:解读手法与禁忌,撰写员和终审员读
- `references/dossier_template.md`:档案结构模板,撰写员读

脚本(都在 `scripts/`,用法见脚本开头注释):

- `split_text.py`:底本切回、切句段并编号
- `verify.py`:核验场景 JSON 与档案里的引文、标签
- `collect_character.py`:别名归一、全文检索命中、按人物聚合

## 你(编排者)怎么用

你是总指挥,不亲自写抽取、不亲自审稿。你的职责是:准备工作区、调度角色、把门、向用户汇报。

**调度原则**:

- 每个角色单独起一个子代理(或单独的会话),只把它需要的文件路径交给它,**不要**转述别的角色的思考过程。
- 撰写员与审稿员尽量用不同模型。抽取和场景审稿量大,可以用较便宜的模型;终审和解读用最强的模型。
- 环境没有子代理时,见文末「降级方案」。

## 开始之前:向用户确认

缺什么问什么,每次只问最必要的:

1. **底本文本**:用户是否已提供 `.txt` 全文?哪个版本(百回本、百二十回本、七十回本)?简体还是繁体?本 skill 不会凭记忆生成原文,**没有底本就不能开工**。请用户提供文件,或确认工作区里已有 `text/`。
2. **要查的人物**:一个或几个。
3. **是否有评点本文本**(金圣叹、李卓吾批语):没有就不做「评点」层,档案里注明。

底本里简繁、异体字要与用户给你的人物名一致,否则全文检索会漏。必要时先让用户统一。

## 流程

### 阶段 0:搭工作区(一次性,换底本才重做)

```bash
python scripts/split_text.py --src <底本文件或目录> --ws workspace
```

检查输出:回数是否符合预期(百回本 100,百二十回本 120);抽查两三回开头结尾是否完整。回数不对时先找原因(目录混入、标题格式不同),不要硬往下走。

### 阶段 1:人物库

1. 创建 `workspace/data/characters.json`(格式见 `schema.md` 第 2 节)。
2. 先建**用户要查的人物**的条目:本名、绰号、化名、称呼变体。可以由你起草,但**必须请用户过目**,尤其是 `ambiguous_aliases`(重名与泛称)。别名表是整个系统的地基,错一处会错一路。
3. 其余人物在抽取过程中由 `new_characters` 上报,你每处理完几回就合并一次,仍需标记「待核」。

用 `python scripts/collect_character.py resolve <名字> --ws workspace` 确认别名归一正确。

### 阶段 2:定范围(懒抽取)

不必先把全书抽完。只抽与目标人物相关的回:

```bash
python scripts/collect_character.py hits <人物> --ws workspace
```

得到命中章回和「尚未抽取」清单。再补两类回目:

- 命中回的**前一回与后一回**(人物常在邻回被提及或有伏笔)
- 用户明确想关注的关系对手方的出场回

把最终清单告诉用户,并给出预估工作量(回数)。回数很多时建议先抽前几回做试点,用户满意后再全量。

### 阶段 3:抽取 + 场景审稿(逐回)

对清单里每一回,循环:

```
抽取员(role_extractor.md) → 写 scenes/chNNN.json
        ↓ verify.py scenes 自检通过
场景审稿员(role_scene_reviewer.md) → 写 reviews/chNNN.review.json
        ↓
   pass? ──是──→ 定稿
     │否
     └→ 抽取员按意见修改 → 再审(最多 3 轮)
```

规则:

- 抽取员完成后必须先让 `verify.py scenes` 通过,才可送审。
- 场景审稿员第一步也要自己跑一遍脚本。
- 第 3 轮仍有 must 问题:写入 `reviews/unresolved.md`,继续往下走,不死循环。
- 每处理完一批,汇总 `new_characters`,更新人物库。**人物库变了,受影响的回要重跑别名归一**(至少检查那几回)。
- 并发:不同回目之间互不依赖,可以并行。同一回的抽取与审稿必须串行。

**试点要求**:第一次使用,先只做 2–3 回,把场景 JSON 和审稿意见给用户看,确认格式和颗粒度合意,再放量。

### 阶段 4:聚合

```bash
python scripts/collect_character.py bundle <人物> --ws workspace
```

核对输出:场景数是否合理?`counterparts` 里有没有明显缺失的重要关系人?有疑问回到阶段 3 补抽。

### 阶段 5:撰写 + 终审(回路)

```
撰写员(role_dossier_writer.md) → dossiers/<人物>.md
        ↓ verify.py dossier 自检通过
终审审稿员(role_final_reviewer.md) → dossiers/<人物>.review.json
        ↓
   pass? ──是──→ 交付
     │否
     └→ 撰写员逐条回应并修改 → 再审(最多 3 轮)
```

规则:

- 撰写员送审前必须让 `verify.py dossier` 通过。
- 终审员第一步也跑脚本,失败直接打回,不浪费人工审稿。
- 撰写员改稿时要写 `revision_log.md`,逐条对应终审意见。
- 第 3 轮仍有 must:把剩余问题作为「未决问题」附在档案末尾,并在汇报里如实说明。

### 阶段 6:交付与汇报

把档案交给用户,附一段简短说明:

- 底本版本、覆盖的回目与场景数
- 审稿经过:场景审稿几轮、终审几轮
- **未决问题与存疑场景**(如实写,不要美化)
- 哪些部分是事实、哪些是推断/猜想,提醒用户按标签判断可信度
- 可以继续深挖的方向(例如某个对手方单独成档)

多个人物时,依次处理,已抽取过的回直接复用。

## 硬规则(对所有角色生效)

1. **底本是唯一事实来源**。评书、影视、游戏、改编、模型自己的记忆都不是。底本里找不到的,不得写成事实或推断。
2. **每条事实性陈述必须带引用标记**:`〔chNNN-sNN：「原文片段」〕`,片段必须是原文连续摘录。
3. **引文由脚本核验**。脚本不通过,不得送审,不得交付。
4. **四层标签不混**:事实、推断、评点、猜想。拿不准就降级。
5. **不用结局倒推动机**;不对白描不写的心理下断言。
6. **没有就写没有**。数组为空、小节写「原文未见」,不要凑数。
7. **审稿员只出意见,不改稿;撰写/抽取员不得审自己的稿**。
8. **做不到的要说**:底本缺失、回目对不上、引文反复核验失败,直接告诉用户,不要糊弄。

## 降级方案(没有子代理时)

- 仍然分角色,但在同一个对话里**严格按顺序**扮演:先抽取员,完成并保存文件;再切换为审稿员,**只重新打开文件和原文,不引用自己刚才的思考**,按「先盲读后对照」执行。
- 盲读时要真的先写出自己的人物清单,再去打开抽取结果比对,不能跳过。
- 同一模型自审不如异模型审稿。尽可能请用户在另一个会话或另一个模型里运行审稿员,并把审稿员的提示文件与待审文件交给它。
- 在汇报里说明:本次审稿为同模型自审,可信度低于独立审稿。

## 常见问题

**用户只问一个小问题(例如「陆谦在哪几回出现」)**:不用跑全流程。用 `hits` 命令给出命中回目,并基于已抽取的场景作答;还没抽取的,告诉用户需要先抽取。

**用户要求没有底本、直接凭记忆写**:说明做不到证据可核对的档案;可以简要回答,但明确标注「未经底本核对」,且不要使用本 skill 的标签体系装作已核验。

**人物重名或称呼歧义严重(如多人被称为「教头」「提辖」「三郎」)**:抽取员必须依据上下文判断并写明依据,拿不准用 `inferred_present`,再由审稿员复核,仍不确定的写入 `unresolved.md`。

**评点本没有**:不做评点层,档案「版本说明」里写明;禁止凭记忆「复述」批语。

**用户觉得档案太长或太细**:调整撰写员的颗粒度(合并相邻场景、只保留 must 级关系),不要放松证据与标签的要求。
