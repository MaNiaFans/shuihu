对 shuihu-dossier.skill 的评审结论

评审对象：[用户提供的原始包](F:/水浒/shuihu-dossier.skill)。本次完整阅读了包内 11 个文件：SKILL.md、7 个参考文件、3 个 Python 脚本；使用当前本地《水浒传》文本运行切回程序，并用合成数据检查引文校验、场景范围、档案格式与聚合状态。原始包及解包后的源码均未修改。

结论：复用价值较高，适合作为项目的初始 skill。角色分工、两轮独立审稿、反方解释和档案结构已经相当具体，可以保留大部分。程序部分目前是原型，尚不能承担其说明中承诺的严格校验和完整性保证。

用户后续明确了实施方向：Agent 模型逐章完整阅读、检校，留下追踪材料与结论，全书完成后再整合复审。因此，本报告的脚本缺陷检查仅评估辅助工具，不评价或代替文学阅读质量。项目优先采用模型阅读、模型检校和原文行号记录；不把“先修整套脚本”作为启动阅读的前置条件。当前有效工作流以[工作流设计](F:/水浒/水浒人物深度解析_工作流设计.md)为准。

这里不以百分比表示“能复用多少”或“准确率多少”：本次没有完成全书人工标注，也没有执行完整的人物档案生成与独立 Agent 审稿；没有依据给出这类数值。

二、已实际复现的程序问题

复现脚本：[check_skill.py](F:/水浒/skill_review/check_skill.py)。机器输出：[results.json](F:/水浒/skill_review/results.json)。合成材料中的“甲方、乙方、丙方”仅用于测试，不属于《水浒传》正文或正式人物库。

1. 切出了 100 回，但附录和现代注释仍作为故事材料进入索引。

用本地底本运行 split_text.py，生成 100 个回文件，同时输出 100 条重复回目警告。该脚本对相同回号直接用后一次覆盖前一次。在这份文件中，不能仅因重复警告就断言正文已丢失；实际确认的问题是末回一直读取到文件结束，附录一、附录二都进入 ch100.txt，第二十九回的现代注释也进入 units。

影响：评论者对人物的评价可与正文混在同一套场景证据中；注释解释和注释中提到的人物也可能被当成故事内容。回数正确不足以证明切分可靠。

定位：[split_text.py 第 69 行起](F:/水浒/skill_review/original/shuihu-dossier/scripts/split_text.py:69)。建议先标记正文、诗词、目录、注释和附录的来源类别，再对正文切回；保留原文件行号、字符范围和校验值。附录仍可作为评点资料使用，但应有独立身份。

2. 场景动作和在场记录没有引文，也能通过检查。

测试将 actions 中的 quote 和 presence_quote 留空，程序返回退出码 0，显示“场景抽取核验全部通过”。原因是 chk 遇到空值直接返回，没有检查必填证据。

定位：[verify.py 第 69 行](F:/水浒/skill_review/original/shuihu-dossier/scripts/verify.py:69)。建议先验证结构和必填证据，再做引文匹配。必须区别“没有这条行动”和“记录了行动但缺少证据”。

3. 省略号前后的引文片段顺序颠倒，仍然匹配成功。

合成原文为“甲方先行。乙方后至。”。合法顺序“甲方先行……乙方后至”通过；倒序“乙方后至……甲方先行”同样返回 True。代码只检查每一段是否存在，没有让下一段从上一段之后继续匹配。

定位：[verify.py 第 45 行](F:/水浒/skill_review/original/shuihu-dossier/scripts/verify.py:45)。建议按顺序、非重叠地匹配省略片段，保存匹配位置；不要把去标点后的匹配误称为逐字原文校验。

4. 模板中的合法排版可以避开事实和推断的检查。

以下两个无证据条目都通过：

```text
- ch001-s01 · 某地 · [事实] 甲方飞天成仙。
- 【多视角对读】[推断] 甲方必然早有预谋。
```

这两种标签位置正是模板采用的形式。校验器只识别列表标记后立即出现的标签；在它之前放入场景号或阅读手法，就不会触发“事实需要引用”“推断需要依据”等检查。完全没有标签的普通断言也不会被拒绝。

定位：[verify.py 第 25 行](F:/水浒/skill_review/original/shuihu-dossier/scripts/verify.py:25)、[第 105 行](F:/水浒/skill_review/original/shuihu-dossier/scripts/verify.py:105)，对照[模板第 21 行](F:/水浒/skill_review/original/shuihu-dossier/references/dossier_template.md:21)与[第 60 行](F:/水浒/skill_review/original/shuihu-dossier/references/dossier_template.md:60)。

建议将待核主张、标签、证据 ID 存为结构化记录，并从记录生成展示文本；若继续直接检查 Markdown，就必须统一模板格式，对未被检查的内容明确报告，不能输出笼统的“全部通过”。程序不能单凭文字格式识别所有事实性主张，语义复核仍然必要。

5. 场景范围没有进行结构检查。

两场景使用重叠区间 [1, 2] 与 [2, 3]，检查通过；只有 3 个句段的测试章节，使用 [500, 600] 且不提供引文，也检查通过。说明中规定的范围不重叠等条件未在程序里实现。

定位：[verify.py 第 39 行](F:/水浒/skill_review/original/shuihu-dossier/scripts/verify.py:39)和[第 59 行起](F:/水浒/skill_review/original/shuihu-dossier/scripts/verify.py:59)，对照[schema.md 第 96 行](F:/水浒/skill_review/original/shuihu-dossier/references/schema.md:96)。建议检查边界、空场景、重复 ID、重叠、缺失句段及其排除原因。短小句段也可能包含关键人物，不能把最多 3 个句段的缺口一概视为可忽略。

6. 聚合不读取审稿状态，也没有完整传递关系人的范围。

在测试中，审稿记录为 verdict=revise，且仍有 must 问题；bundle 命令仍照常生成结果，没有携带审稿状态。测试还显示：仅被提及的乙方进入 counterparts 交集计数；通过关系事件和场外影响关联目标的丙方保留在相应事件数组里，却没有进入 counterparts 列表。

这不是说丙方的事件已经被删除，而是关系人目录与实际关系材料不一致，依赖 counterparts 写人物关系史时容易遗漏。时间字段和 foreshadow 也没有直接进入聚合结果，下游仍需回查场景文件。

定位：[collect_character.py 第 80 行起](F:/水浒/skill_review/original/shuihu-dossier/scripts/collect_character.py:80)。建议区别同场、共同被提及、直接交往和场外关联；从全部关系材料生成关系人目录，并带上状态、覆盖范围和待核项。正式材料应只接收审定记录；有明确保留意见的材料可进入单独的待核区。

正向对照：有效场景与有效引用档案均能通过；完全不在原文中的引文被拒绝；标签处于其支持的位置时，无引用的事实条目也被拒绝。这说明脚本具备部分有效检查，问题是检查范围不完整，而非所有分支都无效。

三、需要修正的方法前提

1. 《水浒传》并非完全没有心理描写或叙述评价。

[SKILL.md 第 10 行](F:/水浒/skill_review/original/shuihu-dossier/SKILL.md:10)与[reading_techniques.md 第 80 行](F:/水浒/skill_review/original/shuihu-dossier/references/reading_techniques.md:80)使用了“不点评、不交代心理”“白描不写心理”的绝对表述。本地第二十九回却明确有“施恩听了，想道”和武松“心中自忖道”；同回还有“可怜这妇人”等叙述用语。[施恩心理描写](<F:/水浒/水浒传 (施耐庵  罗贯中).txt:3368>)、[武松心理描写](<F:/水浒/水浒传 (施耐庵  罗贯中).txt:3390>)、[叙述用语](<F:/水浒/水浒传 (施耐庵  罗贯中).txt:3396>)。

应改为：重视动作、语言和具体细节，也保留原文明示的心理、评价和诗词议论。区分“原文明写的内心活动”“人物自己的解释”与“分析者从行动推测的心理”。不能把原文已经写出的心理也一律归为猜想。

2. 按别名命中和邻回扩展，适合局部试读，不能保证完整生平。

[SKILL.md 第 77 行起](F:/水浒/skill_review/original/shuihu-dossier/SKILL.md:77)采用懒抽取；完整性审查主要检查档案是否包含 bundle 已有条目。两者配合只能证明“已有清单没有漏写”，不能证明“清单没有漏掉全书中的相关事件”。远处的转述、场外决定、称呼歧义和无名人物都可能未进入候选集。

对于其他快速局部查询，可以输出覆盖限定的材料；本项目按用户要求，采用全书逐章完整阅读、检校后再整合的流程。每次记录已读回目、未读回目及未解身份；仅在已核对范围内说“未见”。人物索引用于定位已经读过的材料，不能决定哪些章节值得读。

3. 在场、身份与行为应当分开。

当前 presence 把发言、行动、提及和推断在场放在同一枚举中，并把 mentioned 解释为人不在场。人物可以在场但被他人谈论；认不清某个公人是谁，也不等于不确定他是否在场。建议分别记录在场状态、行为类型、实体匹配候选和证据。明确区分“没有记录台词”与“原文表现了沉默”。

4. 评点是来源，不能与推断强度放在同一个等级中。

保留现有标签易读的优点，但数据中分开记录声音来源和支持程度。人物话语的存在可以确定，其内容仍可能不实；前人评点也可能包含事实、推断或猜想。来源清楚以后才能分析谁在给人物定性，以及这一定性是否与行动相符。

5. 独立审稿和跨回衔接需要实际条件支持。

不同回目并非完全互不依赖：人物表会变化，代词与化名可能需要前文，事件与物件会跨回。可并行处理相对独立的区段，但需要固定的人物表版本、上下文材料和后续统一复核。同一对话中重新扮演审稿员仍受已读内容影响，应如实称为二次复核。

第三轮仍存在问题时，合理做法是停止重复返工，并把受影响的记录隔离、降低成品状态或显示具体缺口。对于事实错误，不能仅通过降为“猜想”或在文末放一条总说明来保留。重试上限与质量放行是两个不同条件。

6. 配角不能在验收时被默认降为次要问题。

终审将遗漏有名对手方列为 must、遗漏无名配角列为 should，而用户的核心要求恰恰包含被忽略的人物。是否必须修复应看它对事件完整性、代价和因果的影响，不能只看有没有姓名。抽查比例也应结合主张的重要性：关键身份、死亡、救助、加害和关系反转等需要逐项核查。

四、按用户澄清后的修订顺序

1. 先明确模型的阅读与检校职责，从第一回开始完整通读，保留充分初读、独立观察、检校意见和修订材料。现有原文行号可以直接用于回查。
2. 建立跨回问题追踪和判断修订记录，按顺序完成全书，不先用姓名命中筛选阅读章节，也不先做浅层编目再决定哪些章节值得细读。
3. 全书完成后，由 Agent 整合人物经历、关系和线索，再由独立 Agent 回到原文复审。途中记录阶段结论，保留反证与未知。
4. 辅助脚本按实际需要再修订。若采用原脚本，必须先处理本报告已复现的相关问题；不采用时，可以继续通过模型阅读、存档与人工可读的证据记录推进。

用户已经提供底本、版本可从文件核查、人物别名可从原文确认时，可直接完成这些确定工作。仅把真正无法消歧且影响结果的问题交给用户。技能里的泛化触发词、固定角色数量和无条件人工过目要求都可以收窄，以服务当前需求。

本次交付是评审、可重复运行的验证脚本与结果。尚未修改或安装原始 skill，也未运行全书语义建档。因此它的实际人物漏检率、解读质量、模型用量与耗时仍待试点测量。
